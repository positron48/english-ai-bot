# Независимое ревью backend диагностики

2026-09-03. Проверены `internal/placement`, `internal/repository/placement_*`, `internal/service/placement_service.go`, `internal/web/placement.go`, миграция 077, `scripts/build-placement-bank.py` и подключение импорта. Ревью исходников; production не затрагивался. Изменения исправляет основной агент.

Итог: основной агент исправил все пять findings; целевые PostgreSQL-регрессии прошли. Названия тестов и подтверждение указаны в `IMPLEMENTATION.md`. В коде уже появились единый порядок блокировок, загрузка банка только для новой сессии и явное истечение попытки с неподдерживаемой политикой. Ниже сохранены исходные сценарии как журнал ревью; окончательное подтверждение исправлений и результатов тестов фиксируется в итоговом отчёте основного агента.

## P1: конкурирующие finish/start могли потерять завершённый результат

Исходный участок: `PlacementAttemptRepository.Start`, выбор active-сессии и `UPDATE ... status='abandoned'`; `Update`, блокировка только `ps`.

Сценарий: `Finish` блокирует сессию; `Start(new_attempt=true)` держит enrollment, читает старый статус active и ждёт блокировки сессии. После commit завершения безусловный `UPDATE WHERE id=?` меняет completed на abandoned. Результат исключается из истории. Для первого сохранения доступа возможен также цикл блокировок: start держит `user_courses FOR UPDATE` и ждёт session; finish держит session и ждёт FK key-share на user_courses.

**Статус:** основной агент сообщил об исправлении: единый порядок `enrollment → session → access`, `FOR UPDATE OF ps` при чтении активной сессии и условие `AND status='active'` при отказе от старой. Нужен/добавляется regression на конкурентные finish/start.

## P2: опубликованные ссылки отзываются не на всех путях выдачи

Участок: `PlacementService.Finish`, фильтр `chapter_ids`; `Get`, `History`, `placementView`.

Первое завершение фильтрует только `chapter.IsPublished`. Глава, чей родительский раздел снят с публикации, остаётся ссылкой. После последующего снятия главы с публикации сохранённый result всё равно отдаётся через Get/History и повторный Finish: фильтр повторно не запускается. В результате диагностика рекомендует недоступные уроки, нарушая требование выдавать только опубликованные ссылки.

Исправление: общий public-view фильтр рекомендаций и review на каждом пути результата по текущей публикации и главы, и её раздела. Исходный диагностический snapshot/score сохраняются неизменными; фильтруется представление.

## P2: восстановление сессии зависит от наличия нового активного банка

Участок: `PlacementService.Start` загружает `s.content.Load` до вызова `attempts.Start`.

Сессия уже содержит вопросы, ключи, резерв и skills в snapshot. Но при временно отсутствующем active bank в DB повторный POST start на другом устройстве выдаёт unavailable ещё до поиска активной сессии или idempotency key. GET по известному id продолжает работать; устройство без этого id не может восстановиться. Это лишняя зависимость закреплённой попытки от актуальной публикации банка.

Исправление: искать существующую попытку в транзакции до загрузки банка; подгружать текущий банк только для создания новой сессии.

## P2: idempotency key не закрепляется при восстановлении существующей активной сессии

Участок: `PlacementAttemptRepository.Start`, ранний `return active, nil` для `!newAttempt`.

Сценарий: A создал сессию с keyA. B вызывает start с keyB и получает ту же сессию; ответ теряется. A заканчивает тест. Повтор start с keyB не находит такой ключ и создаёт новую сессию, хотя повторяется прежний запрос. Ключ учитывается только при фактическом INSERT новой сессии.

Исправление: сохранять соответствие каждого принятого ключа сессии, включая resume, и возвращать ту же сессию при повторе после завершения. Не переписывать единственный исходный ключ: это сломает retry keyA.

## P2: несовместимая версия оценки даёт невосстановимый conflict

Участок: проверки `v.PolicyVersion != placement.PolicyVersion` в Answer/Finish; Get/Start выдачи старой попытки.

После смены версии политики старая active-попытка выдаётся клиенту, но сохранить ответ или завершить её нельзя: API отвечает 409. Клиент предлагает загрузить попытку заново и получает тот же snapshot; это не устраняет несовместимость. Граница версий проверяется правильно, но отсутствует путь восстановления до истечения семи дней.

Исправление: либо обработчик закреплённой версии оценки, либо явное `410 placement_expired` для неподдерживаемой политики на Get/Start/Answer/Finish, позволяющее начать новый тест. Новый результат нельзя тихо пересчитывать новой политикой.

## Проверенные свойства и оставшиеся эмпирические вопросы

- Все обращения к сессии проверяют владельца через `user_courses.user_id`; произвольный идентификатор другого пользователя не открывает ответы. Начальные публичные вопросы не содержат ключа, explanations, level, skill_id или feedback.
- Основная часть — 6 вопросов каждого уровня с квотой 2/2/2 по редакционной сложности. Резерв закрепляется при создании и раскрывается только для выбранного уровня после 30 ответов. Основные ответы после этого закрыты; повтор того же ответа идемпотентен.
- История отбора включает abandoned-попытки и все выданные основной сессией вопросы. Нераскрытый резерв не считается показанным. В рамках попытки семейства исключаются и из основной части, и из уточнений.
- Последние 12 сессий влияют на приоритет семейства, затем при исчерпании берётся самое давнее известное. Поддержка бесконечной уникальности не заявлена. Buildscript требует минимум 16 различных семейств на каждую пару уровень/сложность и минимум 400 вопросов на язык.
- Смена active-версии банка не подменяет сохранённые вопросы или ключи в уже созданной сессии. Импорт сериализован по course и хранит старые версии. Доступ сохраняется внутри транзакции завершения, слабая пересдача не уменьшает накопленный доступ.
- Порог 75% для secure означает 5/6 или 9/12; borderline начинается с 50%. Ограничение изолированного сложного успеха и уточнение пробелов присутствуют. Психометрическая калибровка не выполнена: `estimated=true`, pilot pending и ограничение грамматикой в письменном контексте должны оставаться видимыми.
- Разнообразие навыков внутри уровня сейчас является предпочтением, а не жёсткой квотой: штраф истории сортируется раньше количества выбранных вопросов данного навыка. Для последующей калибровки полезно измерить минимальное фактическое покрытие навыков на последовательных пересдачах реального банка.

Отчёт фиксирует найденное состояние; для закрытия findings требуется сверка исправленного кода и целевых regression tests. Это не утверждение, что перечисленные проблемы остаются после работы основного агента.
