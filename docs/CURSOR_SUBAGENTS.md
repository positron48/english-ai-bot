# Cursor Subagents: сабагенты и пайплайн разработки

Документация по встроенной в Cursor системе **сабагентов** (subagents): как устроены, как создавать и использовать, как задать одну команду для запуска пайплайна разработки с графом вызовов. Документ служит инструкцией для агента при создании и доработке сабагентов и команд.

Официальная документация: [Subagents — Cursor Docs](https://cursor.com/docs/context/subagents).

---

## 1. Что такое сабагенты

**Сабагенты** — это специализированные AI-ассистенты, которым основной агент Cursor может делегировать задачи. Каждый сабагент:

- работает в **своём контекстном окне** (не забивает основной чат);
- выполняет **один тип работ** (исследование, тесты, ревью, деплой и т.п.);
- возвращает **результат родительскому агенту**.

Использование сабагентов позволяет:

- **Дробить сложные задачи** — родительский агент раздаёт подзадачи по ролям.
- **Работать параллельно** — несколько сабагентов можно запустить одновременно.
- **Сохранять контекст** — длинное исследование или логи не засоряют основной диалог.

В чате видно, когда выполнение переходит от одного сабагента к другому (вызовы Task и ответы).

---

## 2. Как это работает

1. Пользователь даёт задачу в чате (или запускает slash-команду).
2. **Родительский агент** решает: выполнить самому или делегировать.
3. При делегировании он вызывает **сабагента** через инструмент Task: передаёт промпт и контекст.
4. Сабагент стартует с **чистым контекстом**; родитель передаёт нужные данные в промпте (история чата сабагенту недоступна).
5. Сабагент работает автономно и возвращает **финальное сообщение с результатом**.
6. Родитель может по результату вызвать следующего сабагента или завершить задачу.

### Режимы: foreground и background

| Режим        | Поведение                                      | Когда использовать                    |
|-------------|-------------------------------------------------|--------------------------------------|
| **Foreground** | Блокирует до завершения, результат возвращается сразу. | Последовательные шаги, когда нужен вывод. |
| **Background**  | Возврат сразу, сабагент работает независимо.   | Долгие задачи или параллельные потоки.   |

Режим задаётся в frontmatter: `is_background: true` для фона.

## 3. Встроенные сабагенты

Cursor уже включает три сабагента — их **настраивать не нужно**:

| Сабагент  | Назначение                    | Зачем вынесен в сабагента |
|-----------|-------------------------------|---------------------------|
| **Explore** | Поиск и анализ кодовой базы   | Много промежуточного вывода, быстрая модель, параллельные поиски. |
| **Bash**    | Выполнение shell-команд       | Объёмный вывод изолирован от родителя. |
| **Browser** | Управление браузером (MCP)    | Шумные снапшоты DOM и скриншоты фильтруются до результата. |

Они вызываются агентом автоматически, когда задача подходит под описание.

---

## 4. Где хранить кастомные сабагенты

| Тип              | Путь                   | Область действия        |
|------------------|------------------------|-------------------------|
| **Проектные**    | `.cursor/agents/`      | только текущий проект   |
| (совместимость)  | `.claude/agents/`      | только текущий проект   |
| (совместимость)  | `.codex/agents/`       | только текущий проект   |
| **Пользовательские** | `~/.cursor/agents/` | все проекты пользователя |
|                  | `~/.claude/agents/`    | все проекты             |
|                  | `~/.codex/agents/`     | все проекты             |

При конфликте имён приоритет: `.cursor/` > `.claude/` > `.codex/`. Проектные перекрывают пользовательские.

Для команд пайплайна разработки в рамках репозитория используем **проектные** сабагенты в `.cursor/agents/`.

## 5. Формат файла сабагента

Каждый сабагент — один **Markdown-файл** с **YAML frontmatter** в начале и текстом промпта ниже.

### Минимальный пример

```markdown
---
name: researcher
description: Исследует кодовую базу и документацию. Используй для сбора требований и поиска существующих решений.
model: inherit
---

Ты — исследователь кода и требований.

При вызове:
1. Уточни цель исследования по контексту от родительского агента.
2. Найди релевантные файлы, API, документацию.
3. Кратко суммируй находки и ограничения.
4. Дай рекомендации по реализации.

Формат ответа: структурированный отчёт (что найдено, что учесть, риски).
```

### Поля frontmatter

| Поле           | Обязательное | Описание |
|----------------|--------------|----------|
| `name`         | Нет          | Уникальный идентификатор (латиница, дефисы). По умолчанию — имя файла без расширения. |
| `description`  | Нет          | Когда вызывать этого сабагента. По описанию родительский агент решает, кому делегировать. |
| `model`        | Нет          | `fast`, `inherit` или ID модели. По умолчанию `inherit`. |
| `readonly`     | Нет          | `true` — сабагент без права записи (только чтение). |
| `is_background`| Нет          | `true` — запуск в фоне, не ждём завершения. |

- **description** критичен для авто-делегирования: формулируй чётко («Используй при …», «Всегда используй для …»).
- Для тяжёлых поисковых задач часто ставят `model: fast`.

## 6. Как использовать сабагенты

### 6.1. Автоматическое делегирование

Родительский агент сам решает, кого вызвать, по:

- сложности и объёму задачи;
- полю `description` у кастомных сабагентов;
- текущему контексту.

Чтобы сабагент чаще выбирали автоматически, в `description` добавляй формулировки вроде: «Use proactively», «Always use for …», «Используй при …».

### 6.2. Явный вызов по имени

В чате можно вызвать сабагента напрямую:

- Через **слэш**: `/researcher разбери текущую архитектуру API`
- Или текстом: «Вызови сабагента researcher, чтобы разобрать архитектуру API».

Имя — из `name` в frontmatter или имя файла (без `.md`).

### 6.3. Параллельный запуск

Один запрос может запустить несколько сабагентов сразу:

- «Параллельно: пусть reviewer проверит последний коммит, а test-runner прогонит тесты».

Агент отправит несколько вызовов Task в одном сообщении.

### 6.4. Паттерн «оркестратор» (пайплайн разработки)

Для пайплайна разработки родительский агент выступает **оркестратором** и по очереди вызывает сабагентов, например:

1. **Researcher** — анализ требований, поиск по коду, ограничения.
2. **Implementer** (или основной агент) — реализация по плану.
3. **Reviewer** — код-ревью, замечания.
4. **Tester** — запуск тестов, фикс падений.
5. **Deployer** (опционально) — проверка деплоя/инструкций.

Каждая «рука» передаёт следующему структурированный вывод (план, список изменений, отчёт о тестах и т.д.). В чате видно переключение между сабагентами по сообщениям Task/результат.

**Одна команда на весь пайплайн** задаётся через slash-команду (см. раздел 8).

## 7. Примеры сабагентов для пайплайна

Ниже — шаблоны, которые можно положить в `.cursor/agents/` и при необходимости доработать.

### 7.1. Researcher (исследователь)

```markdown
---
name: researcher
description: Исследует кодовую базу и требования. Используй в начале пайплайна для сбора контекста и плана.
model: fast
---

Ты — исследователь кода и требований.

При вызове:
1. Пойми задачу из контекста родительского агента.
2. Найди релевантные файлы, API, конфиги, документацию.
3. Выяви ограничения, зависимости, риски.
4. Сформируй краткий план реализации (шаги, файлы, порядок).

Ответ: структурированный отчёт (цель, находки, план, риски). Без кода — только анализ и план.
```

### 7.2. Reviewer (ревьюер)

```markdown
---
name: reviewer
description: Проводит код-ревью. Используй после реализации для проверки стиля, безопасности и соответствия требованиям.
model: inherit
---

Ты — код-ревьюер.

При вызове:
1. Опирайся на контекст от родителя (что сделано, план).
2. Проверь стиль, именование, границы модулей.
3. Обрати внимание на ошибки, утечки, небезопасные места.
4. Отметь несоответствие требованиям или плану.

Ответ: список замечаний по приоритету (критично / важно / рекомендация), с указанием файлов и мест.
```

### 7.3. Tester (тестировщик)

```markdown
---
name: test-runner
description: Запускает тесты и чинит падения. Используй после изменений кода для проверки.
model: fast
---

Ты — специалист по тестам.

При вызове:
1. Запусти релевантные тесты (unit/integration по контексту).
2. Разбери падения: причина, место, как починить.
3. Внеси минимальные правки, сохраняя смысл тестов.
4. Перезапусти тесты и подтверди зелёный статус.

Ответ: сколько прошло/упало, что починено, краткий итог.
```

### 7.4. Verifier (верификатор)

```markdown
---
name: verifier
description: Проверяет, что заявленная работа действительно сделана и работает. Используй после завершения задач.
model: fast
---

Ты — верификатор. Твоя задача — убедиться, что заявленное выполнено.

При вызове:
1. Пойми, что было заявлено сделать (из контекста родителя).
2. Проверь наличие кода, конфигов, тестов.
3. По возможности запусти проверки/тесты.
4. Укажи: что подтверждено, что не найдено или сломано.

Ответ: что проверено и ОК; что не так — конкретно и по шагам исправления.
```

### 7.5. Deployer (деплой)

```markdown
---
name: deployer
description: Проверяет деплой и окружение. Используй для проверки инструкций, Docker/k8s, переменных окружения.
model: inherit
---

Ты — специалист по деплою и окружению.

При вызове:
1. По контексту родителя пойми, что деплоить/проверить.
2. Проверь Dockerfile, манифесты, env, скрипты деплоя.
3. Укажи на несоответствия best practices и типичные ошибки.
4. Дай краткий чеклист для ручного деплоя при необходимости.

Ответ: список проверок, замечания, рекомендации.
```

## 8. Команда на запуск пайплайна разработки

Чтобы **одной командой** запускать весь пайплайн (researcher → implement → reviewer → test-runner → при необходимости deployer), используется **slash-команда** в `.cursor/commands/`.

### 8.1. Где хранить команды

- **Проектные**: `.cursor/commands/<имя>.md`
- Имя файла (без `.md`) = имя команды. Вызов в чате: `/имя`.

### 8.2. Формат файла команды

Обычный Markdown: в теле файла — промпт, который получит агент при вызове команды. Frontmatter у команд не обязателен (в отличие от сабагентов).

### 8.3. Пример команды пайплайна

Файл: `.cursor/commands/dev-pipeline.md`

```markdown
Запусти полный пайплайн разработки для текущей задачи.

Контекст задачи возьми из последних сообщений в чате или уточни у пользователя.

Пайплайн выполни по шагам, делегируя сабагентам:

1. **Researcher** — исследовать кодовую базу и требования, сформировать план реализации. Дождись результата.
2. По плану от researcher **реализуй изменения** сам (или делегируй implementer, если такой сабагент есть).
3. **Reviewer** — провести код-ревью сделанных изменений. Дождись результата.
4. **Test-runner** — запустить тесты и починить падения. Дождись результата.
5. При необходимости **Verifier** — проверить, что заявленное сделано и работает.
6. Если задача касается деплоя/окружения — **Deployer** — проверить конфиги и инструкции.

После каждого шага передавай следующему сабагенту структурированный контекст (план, список изменённых файлов, вывод тестов и т.д.).

Итог пайплайна: краткий отчёт (что сделано, что проверено, что осталось или требует внимания пользователя).
```

Пользователь в чате вводит `/dev-pipeline` (и при необходимости дописывает задачу) — агент начнёт оркестрацию и в чате будет видно переключение между сабагентами.

## 9. Рекомендации и антипаттерны

### Рекомендации

- **Один сабагент — одна роль.** Не делай «универсального помощника».
- **Время на description.** От него зависит, когда агент будет вызывать сабагента. Тестируй на разных промптах.
- **Короткие промпты.** Чётко и по делу, без воды.
- **Версионировать `.cursor/agents/`** в репозитории, чтобы командой пользовалась вся команда.
- **Сначала 2–3 сабагента**, потом добавлять по мере появления явных сценариев.

### Антипаттерны

- Десятки сабагентов с размытыми описаниями («помощник по коду») — агент не поймёт, кого вызывать.
- **Размытый description**: «Use for general tasks» → лучше «Use when implementing OAuth flows».
- **Огромные промпты** — не делают сабагента умнее, только медленнее.
- **Дублирование slash-команд**: если задача одноразовая и без изоляции контекста, достаточно команды в `.cursor/commands/`, без сабагента.
- **Вложенные сабагенты** — сабагент не может запускать другого сабагента (один уровень).

## 10. Инструкция для агента: создание сабагентов и команды пайплайна

При запросе пользователя «создай сабагентов и команду пайплайна» или «добавь сабагента X» действуй по следующему чеклисту.

### 10.1. Создание одного сабагента

1. Определи **роль** и **имя** (латиница, дефисы), например `security-auditor`, `researcher`, `reviewer`.
2. Создай или обнови файл в `.cursor/agents/<name>.md`.
3. В начале файла добавь YAML frontmatter:
   - `name` (если хочешь отличаться от имени файла),
   - `description` — чётко, когда вызывать (для авто-делегирования),
   - при необходимости: `model`, `readonly`, `is_background`.
4. Ниже frontmatter напиши промпт: кто ты, что делать при вызове, в каком формате отвечать. Кратко и по делу.
5. Не создавай сабагентов-дублёров и не раздувай число ролей без явной необходимости.

### 10.2. Создание набора сабагентов для пайплайна

1. Выбери роли под пайплайн (например: researcher, reviewer, test-runner, verifier, deployer).
2. Для каждой роли создай файл в `.cursor/agents/<role>.md` по формату из раздела 5 и примерам из раздела 7.
3. Убедись, что в `description` указано, на каком шаге пайплайна или при какой задаче вызывать сабагента (чтобы оркестратор мог последовательно их вызывать).

### 10.3. Создание команды запуска пайплайна

1. Создай файл в `.cursor/commands/<command-name>.md` (например `dev-pipeline.md`).
2. В теле файла напиши **один промпт** для родительского агента, в котором:
   - явно перечислены шаги пайплайна по порядку;
   - указаны имена сабагентов (как в `name` или имени файла);
   - указано, что после каждого шага нужно дождаться результата и передать контекст следующему;
   - задан ожидаемый итог (отчёт, список изменений, статус тестов и т.д.).
3. Имя команды для пользователя = имя файла без `.md` (вызов: `/dev-pipeline`).

### 10.4. Проверка

- Убедись, что все файлы в `.cursor/agents/` и `.cursor/commands/` валидны (корректный YAML во frontmatter сабагентов, читаемый Markdown).
- Напомни пользователю: вызвать команду в чате через `/имя-команды` и при необходимости описать задачу; в чате будет видно переключение между сабагентами.
