3. **Размер партии:** по четыре главы одного языка по последнему поручению пользователя

   Не помечать файл завершённым после выборочной проверки.
4. **Формы глаголов:** отдельная очередь после основных банков, по четыре леммы за партию.

5. **Закрытие:** нет непроверенных или спорных вопросов; повторная проверка завершена;
   изменённые исходники, финальные главы и встроенные копии согласованы.

Одна единица учёта — один исходный JSON-файл. Главу можно считать готовой только после
закрытия её основного файла **и всех** тренировочных файлов. При параллельной работе
координатор заранее распределяет непересекающиеся source, embedded, report и checkpoint
пути; один файл нельзя назначать двум редакторам. Исполнители меняют только назначенные
им файлы, а координатор один обновляет общие документы, сводит checkpoints и запускает
общие проверки. Команды ниже не ставят блокировок и не резервируют задания.

## Команды из корня репозитория

```bash
# Текущее покрытие, отдельно по языкам и банкам.
python3 scripts/grammar-review.py status

# Следующие незакрытые файлы: сначала незавершённые, включая устаревшие отчёты.
python3 scripts/grammar-review.py next --language es --limit 3
python3 scripts/grammar-review.py next --language en --limit 3
python3 scripts/grammar-review.py next --bank verbs --limit 1

# Полная инвентаризация: пути, IDs вопросов, контрольные суммы, путь отчёта.
python3 scripts/grammar-review.py inventory

# Печатает шаблон отчёта по одному точному пути из inventory/next.
python3 scripts/grammar-review.py template --source courses/spanish-grammar/chapters/001.es.grammar.orientation_alphabet_sounds.spanish_alphabet_letter_names/03-questions.json

# Итоговая проверка. Пока остаются незакрытые единицы, ожидается exit code 1.
python3 scripts/grammar-review.py check

# Проверка самого механизма учёта.
python3 -m unittest discover -s scripts -p grammar_review_test.py -v
```

Все команды read-only: они не вызывают LLM, не меняют контент, не создают отчётов,
не обращаются к сети и не запускают фоновые задачи. Вывод `template` сохраняет редактор
через обычное редактирование файла по пути `report` из инвентаризации. Пока файла нет,
единица автоматически считается `pending` — огромная отдельная очередь JSON не нужна.

## Что проверять у каждого вопроса

Перед началом прочитать outline и теорию главы, затем актуальные правила отображения
и проверки соответствующего типа задания. Вопрос должен быть решаем без открытого
текста теории. В рубрике ES `review-questions/RUBRIC.md` полезны критерии качества,
но её старый протокол очереди и автоматического коммита здесь **не применяется**.

- Естественный русский в инструкции; естественный английский/испанский в примере.
- Задание соответствует теме, уровню и изученному материалу.
- Нет ссылок «по блоку», служебных артефактов и требования помнить текст учебника.
- Ответ не раскрыт условием, оформлением или длиной правильного варианта.
- Ровно один допустимый ответ там, где интерфейс ожидает один. Для открытых ответов
  проверить реальные допустимые варианты и механизм их проверки, а не только эталон.
- Остальные варианты правдоподобны, параллельны и не являются альтернативно верными.
- Инструкция соответствует типу задания: не просить устный ответ там, где нужно выбрать.
- Объяснение называет правило и подходит к выбранному ответу; feedback не противоречит
  обновлённым вариантам. Не ссылаться на буквы ответов: порядок может перемешиваться.
- Сохранены диакритика, согласование и смысл перевода. Для глагольных карточек отдельно
  сверить время, наклонение, лицо, число, `surface_form`, варианты и русский перевод.
- Проверить похожие задания на повторы, противоречия и одинаковые ошибки.

Хорошие вопросы не переписывать ради косметики. Не усложнять лексику выше уровня.
Для спорного языкового случая найти авторитетное подтверждение либо поставить `blocked`
с конкретным вопросом; не выдавать предпочтение редактора за единственную норму.

## Редактор → независимый проверяющий → сборка

### Редактор

Работает только в назначенных исходниках, с учётом уже существующего diff.
Сохраняет IDs, порядок вопросов, тип, сложность, привязку к теории и IDs вариантов.
Если исправление требует смены контракта или удаления задания — останавливает этот вопрос
с `blocked`, описывает причину, не удаляет его молча.

Для каждого ID ставит в отчёте `decision: ok | fixed | blocked`; у `fixed` и `blocked`
обязателен `note` с причиной. Не оставляет непрочитанные вопросы как `ok`.
По завершении записывает `editor`, `reviewed_at` и контрольные суммы **проверенного
окончательного** исходника/контекста. Пока вычитка не закончена, остаётся `pending`.

У `training_pack` поле `signature` вычисляется из содержимого и не равно ID вопроса.
Если меняются поля, участвующие в signature, пересчитать её существующей функцией
соответствующего курса и проверить дубликаты. Не запускать `make training-pack`:
он может заново сгенерировать контент через LLM и затереть ручную редактуру.
Runtime ID тренировочного вопроса строится из `chapter_id::theory_block_id::id`;
эти поля должны остаться стабильными.

### Независимый проверяющий

Другой участник/отдельный запуск проверяющего, не сам редактор под другим именем.
Повторно читает **каждый** вопрос, а не только diff, сверяет варианты и ответы с теорией.
Ставит каждому ID `verification: ok | needs_fix`. Замечания идут в `note`.
Если исправления внесены после проверки, проверяющий повторно подтверждает итоговую версию.
Вписывает `verifier`, `verified_at`, `verification_note`; незакрытые замечания запрещают `done`.
Использование субагентов — отдельный способ исполнения этого процесса, не фоновой сервис.

### Сборка и валидация

Для изменённых основных глав из соответствующего сабмодуля:

```bash

bash scripts/validate-chapter.sh <директория-главы>
```

Для всех изменённых файлов: JSON, уникальность идентификаторов, ссылка на теорию,
корректный ответ среди вариантов, отсутствие дубликатов вариантов, полнота исходных IDs.
Для тренировок — соответствие текущему формату `training_pack`, актуальная signature;
для форм глаголов — сохранность покрытия scope/person/number и согласованность форм.
Не считать ручную вычитку выполненной только потому, что JSON прошёл проверку.

В `checks` записываются реальные команда, результат `pass | known_baseline` и краткое
свидетельство. `known_baseline` допустим только для доказанно существовавшей ошибки:
нужны результаты до/после и объяснение, почему новые правки её не добавили. Новый провал
проверки нельзя записать как старый. Финальные сборки и тесты фиксировать в отчёте партии.

Синхронизация встроенных данных выполняется координатором после партии. Полные скрипты
`scripts/generate-grammar-bundle.sh <en|es>` и `scripts/generate-grammar-training-pack.sh <en|es>`
копируют больше одного проверенного файла: сначала проверить diff и не захватить чужие
незавершённые изменения. При грязном дереве синхронизировать только разрешённые файлы.
Сравнить содержимое source → final → bundle; training source → embedded pack.

Тесты затронутого приложения:

```bash
go test ./internal/grammarbundle ./internal/repository -run 'TestValidateEmbeddedBundleID|TestGrammar.*Bundle|TestGrammar.*Reorder' -count=1
git diff --check
git -C courses/spanish-grammar diff --check
git -C courses/english-grammar diff --check
```

## Когда можно поставить done

У всех вопросов есть решение редактора и подтверждение проверяющего, отсутствуют
`pending`, `blocked`, `needs_fix`; указаны разные исполнители и даты, вывод проверяющего,
проверки с доказательствами. Только тогда `phase: done`.

Скрипт проверяет полноту **записанных свидетельств**, но не может доказать, что человек/LLM
действительно внимательно прочитал текст или что приложенный лог правдив. Это обязанность
редактора и проверяющего. Нельзя автоматически проставить всем `ok` скриптом.

Изменение source или теории автоматически делает отчёт `stale`. Нельзя просто обновить
контрольную сумму: сначала повторно проверить затронутые вопросы и согласованность файла.
Переименование/добавление/удаление вопросов или исходников требует отдельной сверки
инвентаризации; не использовать такие операции, чтобы искусственно уменьшить остаток.

## Контрольная точка и восстановление

`ACTIVE.md` — короткий указатель на текущую партию. JSON-отчёты — решения по каждому
вопросу. Текущие исходники и их контрольные суммы определяют, к какой версии относятся
решения. История чата и суммаризация не подменяют эти три источника.

### Запись после каждых 10–20 вопросов

1. Сохранить правки в назначенном исходнике. Проверить, что JSON читается.
2. Сохранить в существующем отчёте решения **только** по реально прочитанным вопросам;
   остальные оставить `pending`. Записать причины исправлений и сомнений сразу.
3. Если изменения выполнены самим редактором в этой порции, записать соответствующую
   текущую `source_sha256`, сохранив старые решения только для заведомо неизменённых
   вопросов. Изменённые вопросы получают `verification: pending`. Это фиксация
   известной собственной правки, а не разрешение автоматически освежать stale-отчёт.
4. Обновить `ACTIVE.md`: партия и исполнитель; точные source/report пути; следующий
   нерешённый ID; оставшиеся вопросы и замечания; какие сборки, проверки и синхронизации
   ещё нужны; следующая безопасная команда. Для нескольких файлов перечислить их
   отдельно. Решения по вопросам не дублировать в Markdown.
5. Проверить `status --source <путь>`. Не объявлять файл завершённым, пока его статус
   не подтверждён. Даже если агент не успеет обновить `ACTIVE.md`, JSON-отчёт позволяет
   восстановить последний подтверждённый прогресс.

Не ждать конца главы или предупреждения о суммаризации. Перед завершением ответа,
переключением главы и передачей проверяющему тоже обновлять контрольную точку.
Не записывать в неё секреты, содержимое всего диалога и неподтверждённые успехи.

### Чтение после суммаризации или в новой задаче

1. Прочитать `AGENTS.md`, этот документ, `ACTIVE.md` и отчёт активного файла.
2. Проверить текущий diff в корне/сабмодуле и актуальную запись `inventory --source`.
3. При совпадении source/context hashes продолжить с первого `pending`, `blocked`
   или `needs_fix` согласно текущей роли. Не считать следующий ID из `ACTIVE.md`
   достовернее решений в отчёте.
4. Если редактура завершена, но отсутствует независимая проверка, не перечитывать
   файл под новым именем ради `done`. Передать проверяющему при наличии разрешения
   либо честно сохранить `awaiting_verification`.
5. Если hashes не совпадают: сопоставить исходник, отчёт и git diff, определить
   непроверенные изменения. Перепроверить затронутые вопросы; если точную границу
   изменений установить нельзя — перепроверить весь файл. При изменении теории
   перепроверить зависящие от неё вопросы. Только после этого обновлять hashes.

Сбой между записью исходника и отчёта может оставить корректные правки с устаревшим
журналом. Не откатывать их автоматически и не ставить `ok` по факту наличия diff:
повторно прочитать неопределённый участок и восстановить отчёт.

Текущие указания пользователя важнее старого checkpoint. При неясных полномочиях
ограничиться диагностикой и уточнить направление. Старый файл не разрешает push,
деплой, независимые задачи, фоновые запуски или работу в другом checkout.
